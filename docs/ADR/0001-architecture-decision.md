# ADR 0001: Архитектурное решение для SCC

## Статус
Предложено

## Контекст
Текущая кодовая база SCC имеет монолитный `scc.py`, смешанную ответственность, отсутствие стандартизованного разделения слоёв и отсутствие продвинутых инфраструктурных механизмов. Для перехода в коммерческий продукт необходимо формализовать архитектурные решения, сделать систему модульной, безопасной и управляющейся.

## Решение
1. Разделить приложение на слои:
   - Презентация (клиент Windows)
   - Прикладной слой (REST API, токены)
   - Домен (сущности, правила)
   - Инфраструктура (Samba, DB, user management)
2. Произвести рефакторинг `scc.py` в пакеты:
   - `api/` (FastAPI или Flask)
   - `services/`
   - `repositories/`
   - `adapters/` (Samba, Unix)
3. Перейти к PostgreSQL в production, оставить SQLite для локальной разработки. Настроить миграции (Alembic).
4. Добавить безопасное хранение секретов:
   - env vars + файловый backend 600 или HashiCorp Vault
5. Включить TLS и RBAC:
   - HTTPS (nginx + certbot) или встроенный SSL
   - JWT access/refresh, role-based permissions
6. Построить CI/CD + тесты (pytest, интеграционные, security scan)
7. Ввести SRE и DevOps:
   - мониторинг (Prometheus, Grafana)
   - alerts
   - подмены (canary, blue-green)

## Последствия
- Явная модульность снижает риск разрастания технического долга.
- Повышается устойчивость и безопасность.
- Усложняется первоначальная настройка, требуется инфраструктурная автоматизация.

## Альтернативы
- Оставить monolithic `scc.py` и добавить unit-тесты: не масштабируется.
- Использовать Docker compose с SQLite в проде: удобно, но не промышленный уровень.
